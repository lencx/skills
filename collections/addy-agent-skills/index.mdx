<div class="curated-story__lede">
<p class="curated-story__thesis">Its distinguishing feature is not catalog size. Each workflow exposes likely agent rationalizations, red flags, and exit evidence, making engineering discipline inspectable instead of aspirational.</p>
<p>Commands map Define, Plan, Build, Verify, Review, and Ship onto focused Skills and specialist personas. using-agent-skills routes work and enforces assumptions, pushback, scope, and evidence. Individual Skills follow trigger → process → rationalizations → red flags → verification, while commands compose several disciplines without personas recursively invoking personas.</p>
</div>
<section class="curated-story__section curated-story__signature" aria-labelledby="signature-model">
<header class="curated-story__section-heading">
<h2 id="signature-model">Who decides when, how, and from which viewpoint</h2>
<p>The repository separates orchestration from reusable method and specialist judgment. That boundary makes a multi-agent review understandable and prevents personas from recursively creating hidden process.</p>
</header>

<section class="curated-story__section" aria-labelledby="project-mechanisms">
<h2 id="project-mechanisms">Why the workflows are auditable</h2>
<div class="curated-story__mechanisms">
<article><h3>Auditable quality gates</h3><p>Mandatory steps, common excuses and rebuttals, red flags, and explicit exit evidence make each workflow reviewable rather than aspirational.</p></article><article><h3>Staged brownfield adoption</h3><p>Existing codebases start with context, read-only review, and targeted characterization tests instead of loading every Skill or attempting a big-bang rewrite.</p></article><article><h3>Independent doubt cycles</h3><p>Small high-stakes artifacts can be reviewed by a fresh context that receives only the artifact and contract, then reconciles findings against the source.</p></article>
</div>
</section>
<section class="curated-story__section" aria-labelledby="project-practice">
<h2 id="project-practice">Adopt the catalog in stages</h2>
<ol class="curated-story__practice">
<li><p>For an established codebase, begin with context engineering, read-only review, and characterization tests around the next change.</p></li><li><p>Load only Skills for the current phase; the repository explicitly discourages injecting the whole catalog into every session.</p></li><li><p>Use a direct persona for one specialist judgment and a command when several review disciplines need orchestration.</p></li>
</ol>
</section>
<section class="curated-story__section" aria-labelledby="adoption-decision">
<h2 id="adoption-decision">Use the lifecycle selectively, not all at once</h2>
<div class="curated-story__decision">
<div>
<h3>Strong fit for</h3>
<p>Production-oriented teams that want consistent specification, implementation, verification, review, and release gates across greenfield and brownfield codebases.</p>
</div>
<div>
<h3>Keep in scope</h3>
<p>The pack is deliberately prescriptive and phase-heavy. Per-Skill copies may omit shared root references, and host adapters do not provide identical commands, personas, hooks, or plugin behavior.</p>
</div>
