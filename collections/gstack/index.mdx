<div class="curated-story">
<div class="curated-story__lede">
<p class="curated-story__thesis">gstack behaves less like a loose Skill catalog and more like a command-driven startup team. Artifacts travel from product interrogation through real browser QA, deployment health, release documentation, and reflection.</p>
<p>The linked sprint is Think → Plan → Build → Review → Test → Ship → Reflect. Commands adopt distinct organizational roles, while artifacts from office-hours and plan reviews feed downstream engineering, browser QA, release, deployment, canary, and documentation stages. Several stages can mutate code, commit, push, open or merge PRs, and deploy.</p>
</div>
<section class="curated-story__section curated-story__signature" aria-labelledby="signature-model">
<header class="curated-story__section-heading">
<h2 id="signature-model">The linked sprint, end to end</h2>
<p>The important distinction is artifact flow. Upstream product and plan decisions become inputs to engineering, QA, release, and operations instead of being discarded after a chat.</p>
</header>
<div class="curated-signature curated-signature--sprint" data-story-kind="sprint">
<article class="curated-signature__item" style="--story-index:1"><span class="curated-signature__meta">Think</span><h3>office-hours</h3><p>Interrogate the problem, user, and product thesis.</p></article><article class="curated-signature__item" style="--story-index:2"><span class="curated-signature__meta">Plan</span><h3>Executive reviews</h3><p>CEO, engineering, design, DX, and security lenses challenge different assumptions.</p></article><article class="curated-signature__item" style="--story-index:3"><span class="curated-signature__meta">Build</span><h3>Implementation</h3><p>Approved artifacts guide the code change.</p></article><article class="curated-signature__item" style="--story-index:4"><span class="curated-signature__meta">Review</span><h3>Static and independent review</h3><p>Review code and optionally bring in a second model.</p></article><article class="curated-signature__item" style="--story-index:5"><span class="curated-signature__meta">Test</span><h3>Browser QA</h3><p>Reproduce, fix, rerun, and add regression evidence in Chromium.</p></article><article class="curated-signature__item" style="--story-index:6"><span class="curated-signature__meta">Ship</span><h3>PR → deploy → canary</h3><p>Carry the result through CI, production, and post-deploy health.</p></article><article class="curated-signature__item" style="--story-index:7"><span class="curated-signature__meta">Reflect</span><h3>Docs and retrospective</h3><p>Detect stale documentation and feed lessons into the next sprint.</p></article>

<section class="curated-story__section" aria-labelledby="project-mechanisms">
<h2 id="project-mechanisms">Where the sprint goes beyond coding</h2>
<div class="curated-story__mechanisms">
<article><h3>Browser-in-the-loop QA</h3><p>QA drives real Chromium, records defects, fixes them with atomic commits, reruns the failing path, and adds regression tests; qa-only keeps the investigation read-only.</p></article><article><h3>Release work continues after review</h3><p>Ship audits tests and coverage before opening a PR; land-and-deploy waits for CI and deployment, canary observes production, and document-release catches stale docs.</p></article><article><h3>Planning uses distinct executive lenses</h3><p>CEO, engineering, design, DX, and security reviews challenge different assumptions instead of collapsing every concern into one generic planning prompt.</p></article>
</div>
</section>
<section class="curated-story__section" aria-labelledby="project-practice">
<h2 id="project-practice">A low-risk way to evaluate the system</h2>
<ol class="curated-story__practice">
<li><p>Evaluate it with office-hours → plan-ceo-review → review → qa before adopting the entire sprint.</p></li><li><p>Use qa-only or other report-only modes until code changes, commits, pushes, and deployment actions are explicitly authorized.</p></li><li><p>Enable guard for production incidents or any task whose editable subtree must stay narrow.</p></li>
</ol>
</section>
<section class="curated-story__section" aria-labelledby="adoption-decision">
<h2 id="adoption-decision">Separate report-only use from delivery authority</h2>
<div class="curated-story__decision">
<div>
<h3>Best suited to</h3>
<p>Technical founders and small teams that want one Claude Code environment to cover product framing, implementation review, live QA, release, deployment, documentation, and retrospectives.</p>
</div>
<div>
<h3>Authority boundary</h3>
<p>The primary experience is Claude Code, setup can modify global or committed agent state, and many commands are high-authority mutations. The About text says 23 tools, but the current tree evolves quickly; treat that number as reviewed copy, not a live inventory.</p>
</div>
