<div class="curated-story">
<div class="curated-story__lede">
<p class="curated-story__thesis">它的独特性不在目录规模，而在每个工作流都会公开 Agent 常见的合理化借口、红旗和退出证据，让工程纪律可以被检查，而不是停留在口号。</p>
<p>命令将 Define、Plan、Build、Verify、Review 与 Ship 映射到专注 Skills 和专业 personas。using-agent-skills 负责路由，并约束假设、技术反驳、范围和证据；单个 Skill 遵循触发 → 流程 → 合理化借口 → 红旗 → 验证，命令可以组合多项纪律，但 persona 不递归调用 persona。</p>
</div>
<section class="curated-story__section curated-story__signature" aria-labelledby="signature-model">
<header class="curated-story__section-heading">
<h2 id="signature-model">谁决定何时做、如何做、从什么视角做</h2>
<p>仓库把流程编排、可复用方法和专家判断分开。这个边界让多 Agent 评审可以被理解，也防止 persona 递归产生隐藏流程。</p>
</header>
<div class="curated-signature curated-signature--responsibilities" data-story-kind="responsibilities">
<article class="curated-signature__item" style="--story-index:1"><span class="curated-signature__meta">何时</span><h3>Command</h3><p>把 Define、Plan、Build、Verify、Review、Ship 等生命周期阶段映射到多项能力。</p></article><article class="curated-signature__item" style="--story-index:2"><span class="curated-signature__meta">如何</span><h3>Skill</h3><p>提供一种可复用流程，包含触发条件、步骤、合理化借口、红旗和验证。</p></article><article class="curated-signature__item" style="--story-index:3"><span class="curated-signature__meta">谁来判断</span><h3>Persona</h3><p>提供一种专家评审视角，但不会递归编排更多 personas。</p></article>
</div>

<section class="curated-story__section" aria-labelledby="project-mechanisms">
<h2 id="project-mechanisms">这些工作流为何可审计</h2>
<div class="curated-story__mechanisms">
<article><h3>可审计的质量门槛</h3><p>强制步骤、常见借口与反驳、红旗及明确退出证据，让每项工作流都能被检查，而不是停留在口号。</p></article><article><h3>分阶段 Brownfield 采用</h3><p>既有代码库从上下文、只读评审和针对下一次变更的特征测试开始，避免一次加载全部 Skills 或大爆炸重写。</p></article><article><h3>独立怀疑循环</h3><p>小型高风险产物可交给新上下文，只提供产物和契约，再把发现重新与一手内容核对。</p></article>
</div>
</section>
<section class="curated-story__section" aria-labelledby="project-practice">
<h2 id="project-practice">分阶段采用这套目录</h2>
<ol class="curated-story__practice">
<li><p>既有代码库先做 context engineering、只读评审，以及围绕下一项改动的 characterization tests。</p></li><li><p>只加载当前阶段需要的 Skills；仓库明确反对每次会话都注入完整目录。</p></li><li><p>只需一种专家判断时直接使用 persona，需要组合多种评审纪律时使用命令。</p></li>
</ol>
</section>
<section class="curated-story__section" aria-labelledby="adoption-decision">
<h2 id="adoption-decision">按阶段使用生命周期，不要一次全量加载</h2>
<div class="curated-story__decision">
<div>
<h3>适合</h3>
<p>希望在 Greenfield 与 Brownfield 仓库中统一规格、实现、验证、评审和发布门槛的生产型团队。</p>
</div>
<div>
<h3>注意边界</h3>
<p>这套方法刻意具有规定性且阶段较多。单独复制某个 Skill 可能漏掉根目录共享 references，不同 Harness 的命令、personas、hooks 和插件能力也不完全一致。</p>
</div>
</div>
</section>
