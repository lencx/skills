<div class="curated-story">
<div class="curated-story__lede">
<p class="curated-story__thesis">gstack 与其说是松散的 Skills 目录，不如说是一支被命令化的创业团队：产物从产品追问一路流向真实浏览器 QA、部署健康、发布文档和复盘。</p>
<p>其关联 Sprint 是 Think → Plan → Build → Review → Test → Ship → Reflect。不同命令分别承担组织角色，office-hours 与各类 plan review 的产物会传递给工程、浏览器 QA、发布、部署、canary 和文档阶段；其中多个阶段能够改代码、提交、推送、创建或合并 PR，甚至部署。</p>
</div>
<section class="curated-story__section curated-story__signature" aria-labelledby="signature-model">
<header class="curated-story__section-heading">
<h2 id="signature-model">首尾相连的完整 Sprint</h2>
<p>真正的区别是产物流转：上游产品与计划决策会成为工程、QA、发布和运维的输入，而不是在一次对话后被丢弃。</p>
</header>
<div class="curated-signature curated-signature--sprint" data-story-kind="sprint">
<article class="curated-signature__item" style="--story-index:1"><span class="curated-signature__meta">Think</span><h3>office-hours</h3><p>追问问题、用户与产品判断。</p></article><article class="curated-signature__item" style="--story-index:2"><span class="curated-signature__meta">Plan</span><h3>多视角计划评审</h3><p>CEO、工程、设计、DX 和安全视角分别挑战不同假设。</p></article><article class="curated-signature__item" style="--story-index:3"><span class="curated-signature__meta">Build</span><h3>实现</h3><p>已确认的产物指导代码修改。</p></article><article class="curated-signature__item" style="--story-index:4"><span class="curated-signature__meta">Review</span><h3>静态与独立评审</h3><p>评审代码，并可按需引入第二模型。</p></article><article class="curated-signature__item" style="--story-index:5"><span class="curated-signature__meta">Test</span><h3>浏览器 QA</h3><p>在 Chromium 中复现、修复、重跑并增加回归证据。</p></article><article class="curated-signature__item" style="--story-index:6"><span class="curated-signature__meta">Ship</span><h3>PR → 部署 → Canary</h3><p>让结果穿过 CI、生产部署和上线后健康检查。</p></article><article class="curated-signature__item" style="--story-index:7"><span class="curated-signature__meta">Reflect</span><h3>文档与复盘</h3><p>发现过期文档，并把经验带入下一轮 Sprint。</p></article>
</div>

<section class="curated-story__section" aria-labelledby="project-mechanisms">
<h2 id="project-mechanisms">这条 Sprint 如何超越写代码</h2>
<div class="curated-story__mechanisms">
<article><h3>浏览器进入主 QA 流程</h3><p>QA 驱动真实 Chromium，记录缺陷、以原子提交修复、重跑失败路径并增加回归测试；qa-only 保留纯报告模式。</p></article><article><h3>发布闭环不止于 Review</h3><p>Ship 在开 PR 前审计测试和覆盖率；land-and-deploy 等待 CI 与部署，canary 观察线上，document-release 检查过期文档。</p></article><article><h3>规划使用不同组织视角</h3><p>CEO、工程、设计、DX 与安全评审分别挑战不同假设，不把所有问题压缩成一个泛化 planning prompt。</p></article>
</div>
</section>
<section class="curated-story__section" aria-labelledby="project-practice">
<h2 id="project-practice">低风险评估这套系统</h2>
<ol class="curated-story__practice">
<li><p>先用 office-hours → plan-ceo-review → review → qa 低成本体验，再决定是否采用完整 Sprint。</p></li><li><p>在明确授权修改代码、提交、推送和部署前，优先使用 qa-only 等纯报告模式。</p></li><li><p>生产事故或严格限定改动范围的任务使用 guard。</p></li>
</ol>
</section>
<section class="curated-story__section" aria-labelledby="adoption-decision">
<h2 id="adoption-decision">区分纯报告使用与交付权限</h2>
<div class="curated-story__decision">
<div>
<h3>最适合</h3>
<p>希望一个 Claude Code 环境覆盖产品思考、实现评审、实时 QA、发布、部署、文档和复盘的技术创始人或小团队。</p>
</div>
<div>
<h3>权限边界</h3>
<p>主要体验围绕 Claude Code，安装可能修改全局或受跟踪的 Agent 状态，且多个命令拥有高权限写操作。About 中的 23 应作为受控描述保留，而不能当作实时清单数量。</p>
</div>
</div>
</section>
