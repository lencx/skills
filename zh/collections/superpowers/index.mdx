<div class="curated-story">
<div class="curated-story__lede">
<p class="curated-story__thesis">安装 Superpowers 等于接受一套带硬门槛的开发制度：设计确认、隔离环境、TDD、独立评审和新鲜验证都是要求，而不是可选技巧。</p>
<p>Brainstorming 与人工设计确认是规划和编码前的硬门槛。实现随后进入隔离 worktree，以 TDD 执行窄任务，并把实现者自审、规格评审和代码质量评审分开；只有刚刚重新执行且读完结果的证明命令，才能支持完成声明。</p>
</div>
<section class="curated-story__section curated-story__signature" aria-labelledby="signature-model">
<header class="curated-story__section-heading">
<h2 id="signature-model">一项改动在完成前必须通过的路径</h2>
<p>顺序之所以重要，是因为每个门槛都会生成下一步依赖的证据。即使改动看起来很小，跳步仍被视为流程失败。</p>
</header>
<div class="curated-signature curated-signature--hard-gates" data-story-kind="hard-gates">
<article class="curated-signature__item" style="--story-index:1"><h3>梳理问题</h3><p>澄清意图并比较方案。</p></article><article class="curated-signature__item" style="--story-index:2"><h3>确认设计</h3><p>在规划之前由人确认预期行为。</p></article><article class="curated-signature__item" style="--story-index:3"><h3>隔离环境</h3><p>使用 worktree 并建立干净基线。</p></article><article class="curated-signature__item" style="--story-index:4"><h3>拆解计划</h3><p>写出包含文件和证明命令的窄任务。</p></article><article class="curated-signature__item" style="--story-index:5"><h3>TDD</h3><p>通过 red、green、refactor 实现。</p></article><article class="curated-signature__item" style="--story-index:6"><h3>两层评审</h3><p>先检查规格符合性，再检查代码质量。</p></article><article class="curated-signature__item" style="--story-index:7"><h3>重新验证</h3><p>在声明完成前立即重跑证明命令。</p></article>
</div>

<section class="curated-story__section" aria-labelledby="project-mechanisms">
<h2 id="project-mechanisms">这些门槛为何不可省略</h2>
<div class="curated-story__mechanisms">
<article><h3>设计确认是硬门槛</h3><p>即便是小型行为变更，也要先解决意图、备选方案和可读设计，之后才能开始脚手架、规划或实现。</p></article><article><h3>实现与评审职责分离</h3><p>每个任务都依次经历实现、自审、规格符合性评审、代码质量评审，并在修复后重新评审。</p></article><article><h3>验证必须时间新鲜</h3><p>只有刚刚重新运行证明命令，并读完完整输出和退出状态，才能支持完成声明。</p></article>
</div>
</section>
<section class="curated-story__section" aria-labelledby="project-practice">
<h2 id="project-practice">用一项真实改动试运行</h2>
<ol class="curated-story__practice">
<li><p>先完成 brainstorming 和设计确认，再让 Agent 编写实现计划。</p></li><li><p>优先复用现有隔离环境，修改前运行项目 setup 与 baseline tests。</p></li><li><p>坚持 red、green、refactor，并在声明完成前重新执行能直接证明结论的命令。</p></li>
</ol>
</section>
<section class="curated-story__section" aria-labelledby="adoption-decision">
<h2 id="adoption-decision">采用它会改变工作如何被批准</h2>
<div class="curated-story__decision">
<div>
<h3>值得承担成本的场景</h3>
<p>需要严格规格、隔离实现、TDD、子代理协作与评审闭环的功能开发或 Bug 修复。</p>

<h3>流程冲突</h3>
<p>其仓库把这些工作流定义为 mandatory，而非可选建议。采用前应确认这种流程接管程度符合项目既有规则。</p>
